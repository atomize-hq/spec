## Problem Statement

You want a development model where software is authored as structured semantic records rather than loose text files. Spec files capture intent, contracts, dependencies, and native code in annotated YAML containers. This forces AI into a verify-as-it-builds workflow and creates a single source of truth that is both human-readable and machine-operable.

The first milestone is proving the source model works: authors can write `.unit.spec` files, the system validates them through CUE schemas, and produces a normalized internal representation.

---

## What Makes This Cool

The core delight is **explicit structure as a forcing function**. Every meaningful code unit carries:
- Why it exists (intent)
- What it promises (contract, deps)
- How it's implemented (native code)
- How to verify it (local tests)

This isn't just documentation - it's a workflow constraint. AI cannot freehand large changes because it must work within the semantic structure: validate fields → compile → test → iterate.

The canonical source is machine-readable from day one. Planning docs can reference it, tools can query it, and the system can evolve it.

---

## Constraints

- Start minimal: functions only, Rust only
- Skip `.test.spec` initially - embed local tests in the unit
- YAML authoring surface with CUE validation
- Native code lives inside YAML structure, not vice versa
- Authoring experience matters more than optimization

---

## Premises

1. **Semantic units wrap native code in YAML containers** - The structure (intent, contract, deps) is YAML, but implementation lives in native code blocks like `body.rust:`. The semantic layer augments rather than replaces target languages.

2. **M1 proves the source model before code generation** - Can authors write valid `.unit.spec` files? Does CUE validation work? Can we normalize to a canonical internal representation? Runtime comes after authoring works.

3. **AI safety comes from workflow constraints** - The AI must validate → compile → test → iterate. It works in unit-sized increments with explicit verification, not freehand edits.

4. **Native code generation must be readable** - Generated code should look human-written. This is about making software more legible, not creating a new language.

---

## Approaches Considered

### Approach A: Minimal Core (RECOMMENDED)
Start with just functions and just Rust. Smallest surface: `unit.spec` files with id, kind, intent, and `body.rust`. Embed local tests directly in the unit. Skip separate `.test.spec` files for now.

**Pros:**
- Ships fastest (days, not weeks)
- Proves core loop: author → validate → normalize
- Establishes CUE → YAML → IR pipeline
- Small enough to iterate on schema based on real usage

**Cons:**
- Only covers happy path initially
- No separate test files or broader verification layers
- Misses early validation of the full planned surface

**Reuses:** None - this is a greenfield architecture.

### Approach B: Complete Source Model
Both `.unit.spec` and `.test.spec` from day one. Support functions and components. Full contracts with inputs/outputs. Local atom tests owned by units, broader tests as separate files. Dependency declarations with referential integrity.

**Pros:**
- Proves the full source model before M2
- Validates all the concepts from architecture doc
- No rework when expanding to broader verification

**Cons:**
- Bigger upfront investment delays proving the core loop
- More CUE schemas to maintain before usage data
- Risk of over-designing the surface before validating it

### Approach C: Validator-First
Focus entirely on validation experience. Rich CUE schemas for all planned unit kinds. Excellent error messages (think rustc, not generic YAML validation). CLI that guides authors toward correct structure.

**Pros:**
- Best author experience
- Establishes quality bar early
- Most defensible architecture

**Cons:**
- Delays any code generation further
- Validation without runtime feels like a toy
- May over-invest in error messages before schema stabilizes

---

## Recommended Approach

**Choose Approach A: Minimal Core.**

Release 0.1 should prove the smallest viable source model: authors write `*.unit.spec` files, they validate through CUE, and normalize to a stable internal representation. Expand to `.test.spec`, broader unit kinds, and code generation in subsequent releases.

This follows the roadmap's M1 (Semantic Source Foundations) with intentional narrowness.

---

## Open Questions

1. **CUE organization:** One schema file per unit kind? Or unified schema with discriminators?
2. **ID format:** Hierarchical (`pricing/apply_discount`) or flat with path metadata?
3. **Native code delimiters:** Markdown fences (```rust) or literal blocks (|)?
4. **Validation ordering:** Fail on first error or collect all diagnostics?

These should resolve during implementation based on what feels ergonomic.

---

## Success Criteria

- Can author a valid semantic unit without internal knowledge
- Invalid source fails with clear CUE-based diagnostics  
- Valid source normalizes to canonical internal representation
- Spec files are readable enough to serve as durable editing surface
- Can process a directory of units and report aggregate status

---

## Distribution Plan

Release 0.1 is a CLI tool distributed via:
- GitHub Releases as a precompiled binary
- Cargo install for Rust users who want to build from source

CI/CD: GitHub Actions workflow that builds release binaries on tag push, generates checksums, and creates GitHub release.
